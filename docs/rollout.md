# Cares：空き情報・応援のハート・良いところ

2026-10-07。今回の変更は本番未適用。既存の星評価をハートに換算しない。

## リリース順序

1. `20261007022927_cares_warm_directory.sql` だけをDBへ適用。3テーブル・3ビュー・1関数と空き情報の追記列を追加する。旧画面の読取権限は維持する。
2. このPRのフロント/APIをプレビューで確認し、本番へ切り替える。ログイン・未ログインで一覧/地図/詳細、空き投稿、ハート、口コミを確認する。DB変更前のプレビューでは新機能の読み取りエラーが正常であり、動作確認完了とは扱わない。
3. 新しい画面/APIの配信確認後、`20261007024047_cares_community_privacy.sql` を適用。公開IP・ユーザーIDの列権限を除き、直接投稿を禁止し、旧星評価を本人だけにする。未認証・認証済み別人・本人・service_roleの読取を検証する。
4. SupabaseのAdvisorを確認。旧OS側のCares関連読取を含め、本番の共有DB利用経路でエラーが増えていないことを確認する。

**2つを一括適用しない。** 列権限を先に狭めると旧アプリの `select('*')` が失敗する。今回の新API/画面は公開列だけ選択する。旧公開の星の集計は追加DB変更と別にフロントから除外する。

## 意図する動作

- 事業所のハートは公開の応援累計。アカウント登録したユーザーが再び押すと増える。累計/生涯の回数に商品上の上限を設けない。異常な連打は1秒間隔の制限で抑制。
- 応援人数は異なるアカウントの累計。本人の実在確認を意味しない。退会しても公開累計は減らさない。厳密な実人数/介護の質の評価ではない。
- POSTはサーバーの認証結果から本人IDを得て、service_role専用invoker RPCを呼ぶ。同じ request_id の再送は1回扱い。トランザクションとアドバイザリロックで加算を保護。内部イベント/本人IDは一般利用者から読めない。
- numericを文字列で返し、画面ではBigIntで整形。取得失敗を0件に置き換えない。
- 空き情報はログイン・公開確認・情報源・確認日・掲載期限必須。掲載期限は初期7日後、確認日から最大30日。これは初期運用案で、制度上の有効期限ではない。
- 情報源は投稿者申告。「事業所からのFAX」だけで公式認証済みにはならない。事業所のオーナー認証とも別。
- 確認日→投稿日時の順で最新1件を使う。期限切れ/確認日不明は要確認。新しい期限切れから古い空きありを復活させない。JSTの掲載期限当日までは有効。空き情報を返すAPIはno-store。
- 一覧/地図/詳細は同じ最新情報の定義。公式ページは対応する事業所ページへの導線を追加。公式投稿の記事本文や従前の受入目安は過去情報として別に存在する。
- 口コミは実体験の「良かったところ」を促す文面と投稿前確認。専門職の声・本人だけのメモは区別。ネガティブな単語を自動書換え/自動削除しない。事前の内容審査・通報管理画面は今回の実装に含めない。

## 検証

`npm test`（Node + PGliteの実SQL）、`npm run typecheck`、`npm run lint`、`npm run build`。
PGliteは合成の最低限スキーマとロールを使うため、本番のPostgREST・Auth・他アプリの互換性を保証しない。実PostgreSQL複数セッションでの競合試験は別途実施する。

## 切り戻し

機能テーブルと投稿データを削除しない。旧バイナリをそのまま戻すと第2段階の権限と不整合になる。新機能を隠しつつ、公開列の明示選択と旧星の非公開を維持した修正版を用意して戻す。公開権限を広げて復旧しない。
