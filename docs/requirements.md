# Cares：直営のかいごの窓口で使う仕様・改善整理

2026-10-07 / 三浦の今回の依頼に基づく。調査対象は公開Caresと `CS-Ryo6251/cares-portal` の最新main `27587a7`。本番DBは読取のみ。実装した変更はレビュー用ブランチにあり、本番反映済みではない。

## 提案する位置づけ

**「地域の事業所のいま」と「良いところ」が分かり、相談につながる地域の介護情報サイト**にする。かいごの窓口の職員が日々受け取る空き案内・電話確認・訪問で得た情報を、地域の人と共有できる資産に変える。

ハートと良かった体験を中心にする方向を採用する。ただし、何度でも押せるハートの総数は「応援の量」であり、介護の質・本人との相性を直接測る数字ではない。累計を大きく見せつつ、応援人数・具体的な良さ・受入条件を併記する。

## 現状の確認結果

| 項目 | 現状の根拠 | 今回の対応 |
|---|---|---|
| 空き情報 | 匿名の空きあり/なし/不明と短文。確認日・情報源・有効期限がない。直近30日の件数を並べ、相反する情報の新旧が分かりにくい | ログイン・情報源・確認日・掲載期限・受入条件・公開確認を追加。最新情報の判定を一覧/地図/詳細に共通化 |
| 星評価 | 画面では「自分だけ」と説明する一方、トップ/地図は星を公開集計。DBにも公開読取ポリシーあり | 公開の星を廃止し、事業所の応援ハートに置換。旧星は本人用の履歴に残す |
| 既存のハート | `cares_likes` は事業所の記事に対する1人1回のトグル | 事業所そのものへの累計ハートを別データで新設。記事のいいね・お気に入りと区別 |
| 口コミ | 家族/地域の声と専門職の声は既に区分。一般的な感想を自由入力 | 「良かったところ」「連携で助かったこと」に誘導し、実体験と個人情報について投稿前確認 |
| 投稿の不具合 | ログイン時にDBに存在しない `reporter_name` 列へ書き込むコードあり | 不要な氏名の保存を除去。公開は立場のみ |
| 公開権限 | 投稿APIを経由しない直接INSERTと、IPハッシュ/ユーザーIDの直接SELECTが許可されていた | 画面の更新後に適用する別SQLで、公開列のみ読取・サーバー経由投稿へ変更 |

本番の対象テーブル件数は、空き情報 **1件**、口コミ/専門職の声 **0件**、星評価 **1件**。利用者数やMAUを示す数字ではなく、2026-10-07の対象テーブルの単純件数。非公開の投稿本文・利用者情報は出力していない。

本番サイトのHTTP 200を確認。通常の本番ログイン操作・実投稿は未実施。7月の既存PR #2は競合したまま残っていたが、関連する画面改善はmainのPR #5等にも入っており、今回は最新mainを起点にした。PR #2は変更していない。

## 1. 事業所から届いた空き情報

**運用フロー**：案内を受領 → 対象事業所を確認 → 公開可否を確認 → Caresへ入力 → 期限内に再確認/更新。

- 掲載者はログインする。かいごの窓口の職員による代理入力も、この操作で可能。
- 必須：空き状況、情報源、確認日、掲載期限、公開してよい情報であることの確認。
- 情報源：事業所からのFAX/メール、電話確認、事業所の公開情報、訪問時の確認、その他。
- 任意：曜日、人数、送迎範囲、受入条件。初期版では200字の短文。
- 確認日と掲載日は区別する。未来の確認日・存在しない日付は拒否する。
- 掲載期限は初期値7日後、最大で確認日から30日。**運用の初期設定であり、制度上の期限ではない。** 直営1店舗の試行結果で調整する。
- 最新は確認日、同じ確認日なら投稿日時で判定。最新の「空きなし」「要確認」が古い「空きあり」を上書きする。最新情報が期限切れになっても過去の空きありを復活させない。
- 期限切れ・確認日不明は「要確認」。取得失敗と情報未登録は詳細画面で区別。
- 情報源は「投稿者申告」と表示。「FAXを受け取った」という申告からCares確認済み・事業所公式認証を付けない。
- 利用者の氏名・病歴・相談内容を掲載しない。原本FAXやメールは初期版では公開添付しない。

掲載例：**空きあり / 10月7日確認 / 10月14日まで / 事業所からのFAX（投稿者申告） / 火・木に各1名、送迎範囲は応相談**。

## 2. 事業所への応援ハート

- 表示は **♡ 128 / 23人からの応援** のように、累計と人数を並べる。
- 累計に商品上の上限を設けない。ログインした同じ人が別の機会に再び送れる。
- 1秒以内の連打は待ってもらう。同じ通信の再送は加算しない。「1人1票」や累計上限とは別の対策。
- 人数は異なるアカウントの累計。実在する人数の審査・本人確認済み人数ではない。複数アカウント不正への対応は別途必要。
- 誰が応援したかは公開しない。旧星評価をハートへ換算しない。新しい反応として0から開始。
- 詳細で送信し、トップの事業所一覧・地図・検索一覧でも同じ集計を表示。公式ページから対応する事業所ページへ誘導。
- 初期版の並び順は従来の地域/サービス等を維持。ハート順のランキング・自動紹介先選定は入れない。

「一人で何度も押せる」を採用するなら、画面上にもそのことを示す必要がある。押した回数を利用者数や客観的な質として見せない。

## 3. 良いところを書ける口コミ

家族・地域の方には「見学や利用でうれしかったこと」、専門職には「相談や連携で助かったこと」を尋ねる。例文も実体験の具体的な場面にする。

- 星・点数の入力は求めない。
- 投稿者の立場だけを表示。本文中の個人情報は書かないように案内し、投稿前に本人が確認。
- 公開の声と、本人だけの業務メモは区別する。
- 心配事は、事業所の相談窓口・担当ケアマネへの相談導線を案内する。課題を無理に褒め言葉へ書き換えない。
- **今回の実装は投稿を促す設計と確認欄まで。内容を事前審査する機能ではない。** ネガティブ語を機械的に排除すると、感謝を含む複雑な体験も誤って拒否するため、単語ブラックリストは入れない。
- 公開を広げる前に、通報・非公開化の窓口/担当を決める。事業所自身の紹介と第三者の体験は混同しない運用が必要。管理画面・審査キュー・利害関係表示は次段階の仕様。

## 直営1店舗での使い始め方

1. 連携する地域・サービス種別を絞って既存事業所ページを確認する。
2. 職員が受け取った空き案内を、公開可能な項目に絞って手入力する。
3. 訪問や連携で助かった実体験を、本人の言葉で投稿する。架空のハート・口コミで初期件数を作らない。
4. 面談時に「条件に合う候補」「いつ確認したか」「どんな良さがあるか」を一緒に見る。
5. 期限切れの情報が増えるなら、通知や一括更新を追加する。FAX自動抽出は、人が公開内容を確認する経路を設計してからつなぐ。

初期版でできるのは**受領情報の手動掲載**。CareSpace OSの受信FAXからの自動取り込み、原本管理、店舗別の承認権限、期限前通知、代理入力者の認証バッジは未実装。

## 試行で見る指標

実績の基準値はまだない。直営店の試行開始から4週間を初回評価期間とする案。

| 指標 | 分子/分母・計測方法 | 判断 |
|---|---|---|
| 空き情報の鮮度 | 期限内の情報がある対象事業所数 / 試行地域で実際に探す対象事業所数 | 必要な情報が増えているか |
| 掲載までの時間 | 受領から掲載までの経過時間の中央値。原本受領時刻は内部で記録 | 職員の負担に見合うか |
| 探す業務への利用 | Caresで候補を確認した相談件数 / 期間内のサービス探索相談件数（内部集計） | 現場の役に立つか |
| 応援の広がり | ハート累計と異なるアカウント数を別々に観測 | 少数の連打だけになっていないか |
| 情報の誤解 | 期限切れを空きありと受け取った報告、相談先が見つからない報告 | 表示/運用を直す |

技術上の受入条件は、公開に個人の識別情報を含めない、期限切れを検索で空きありに含めない、同一送信を二重加算しない、取得失敗を0件と表示しないこと。導入効果の達成目標は試行の基準値取得後に設定する。
